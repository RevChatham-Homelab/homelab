# Purpose

The primary purpose of CBART is to create reliable, repeatable, and verifiable Recovery Points for the RevChatham Homelab.

This chapter explains what Recovery Points are, why they are important, and how they form the foundation of the application's backup and recovery strategy.

By the end of this chapter, readers should understand how CBART captures critical system information, how Recovery Points are organized, and how they can be used to support disaster recovery efforts.

---

# What is a Recovery Point?

A Recovery Point is a structured snapshot of the homelab environment captured at a specific point in time.

Unlike a traditional backup, a Recovery Point is not intended to store complete copies of virtual machines or container data. Instead, it preserves the information required to rebuild, verify, and recover the environment in a predictable manner.

A Recovery Point combines configuration, documentation, inventory, and verification artifacts into a single, organized directory.

Each Recovery Point represents a known state of the environment and can be archived for future reference or used during recovery operations.

---

# Why Recovery Points Matter

Infrastructure changes over time.

Containers are updated.

Configuration files evolve.

Documentation grows.

New services are deployed.

Without preserving these changes, recovering from hardware failure or accidental data loss becomes significantly more difficult.

Recovery Points reduce this risk by creating consistent records of the environment at regular intervals.

Each Recovery Point serves as a historical record that can assist with:

- Disaster recovery
- Configuration auditing
- Environment reconstruction
- Change tracking
- Documentation preservation
- Recovery validation
- Portfolio documentation

Rather than asking "What did the server look like last month?", a Recovery Point provides the answer.

---

# Recovery Point Naming Convention

Every Recovery Point is assigned a unique identifier.

The naming convention follows the format:

```
RP-YYYYMMDD-###
```

Examples include:

```
RP-20260721-001
RP-20260721-002
RP-20260721-003
```

Each component has a specific purpose.

| Component | Description |
|-----------|-------------|
| RP | Recovery Point identifier |
| YYYYMMDD | Date the Recovery Point was created |
| ### | Sequential Recovery Point number for that day |

This naming convention ensures that Recovery Points remain unique, sortable, and easy to identify.

---

# Recovery Point Philosophy

CBART is designed around the principle that recovery should be predictable.

Every Recovery Point is created using the same process, follows the same directory structure, and includes the same core artifacts whenever possible.

Consistency provides several important benefits.

- Easier validation
- Faster recovery
- Simplified troubleshooting
- Reduced human error
- Repeatable engineering practices
- Improved long-term maintainability

Rather than relying on memory or handwritten notes, Recovery Points provide an organized record of the environment that can be referenced months or even years after they were created.

---

# Recovery Point Structure

Every Recovery Point generated by CBART follows a standardized directory structure.

Maintaining a consistent layout ensures that Recovery Points remain easy to navigate, verify, archive, and restore regardless of when they were created.

A typical Recovery Point appears as follows.

```
RP-YYYYMMDD-###

├── checksums/
├── docker/
├── documentation/
├── logs/
├── manifest/
├── proxmox/
└── verification/
```

Each directory contains information that supports a specific aspect of the recovery process.

---

# Docker Backups

```
docker/
```

The Docker directory contains configuration files required to recreate the application's containerized services.

Depending on the deployed services, this directory may contain items such as:

- Docker Compose files
- Environment file templates
- Service README files
- Container-specific configuration files

Rather than backing up container data directly, CBART preserves the configuration necessary to redeploy services consistently.

This approach keeps Recovery Points lightweight while maintaining reproducibility.

---

# Documentation Archive

```
documentation/
```

The documentation directory contains an archived copy of the project's engineering documentation at the time the Recovery Point was created.

Examples include:

- User manuals
- Engineering standards
- Architecture documents
- Implementation guides
- Recovery documentation
- Supporting Markdown files

Capturing the documentation alongside configuration files ensures that recovery procedures remain synchronized with the environment they describe.

---

# Manifest

```
manifest/
```

Every Recovery Point includes a Recovery Point Manifest.

The manifest serves as the inventory for the Recovery Point and records metadata describing its contents.

Typical information includes:

- Recovery Point identifier
- Creation date and time
- Project information
- Description
- Verification status
- Included artifacts
- Notes

The manifest provides a single location for identifying what was captured during Recovery Point generation.

---

# Proxmox Information

```
proxmox/
```

The Proxmox directory records information about the virtualization environment.

Examples include:

- Host information
- Storage configuration
- Virtual machine inventory
- Backup inventory

These files provide valuable context during disaster recovery by documenting the state of the virtualization platform at the time the Recovery Point was created.

---

# Verification

```
verification/
```

Recovery Points are intended to be verifiable.

The verification directory contains reports documenting the validation process performed after Recovery Point generation.

Typical validation includes:

- File existence checks
- Archive validation
- Manifest validation
- Docker backup verification
- Documentation verification
- Proxmox information verification

Verification reports provide confidence that a Recovery Point was created successfully and contains the expected artifacts.

---

# Checksums

```
checksums/
```

Checksums are generated to protect the integrity of Recovery Point contents.

By comparing stored checksums against calculated values, users can determine whether files have changed or become corrupted.

Checksums help ensure that Recovery Points remain trustworthy over long-term storage.

---

# Logs

```
logs/
```

The logs directory contains execution logs generated while CBART created the Recovery Point.

These logs document:

- Recovery Point creation
- Processing steps
- Warnings
- Errors
- Verification results
- Completion status

Execution logs provide valuable troubleshooting information should Recovery Point generation fail or produce unexpected results.

---

# Putting It All Together

Each directory within a Recovery Point serves a distinct purpose, but together they form a comprehensive snapshot of the homelab's operational state.

Configuration files, documentation, manifests, verification reports, inventories, logs, and integrity checks work together to provide a Recovery Point that is not only restorable, but also understandable and verifiable.

This structured approach allows Recovery Points to serve as both recovery assets and historical records of the environment.

---

# Creating a Recovery Point

Generating a Recovery Point is the primary function of CBART.

During execution, CBART performs a series of automated tasks designed to collect, organize, and verify the information required to recover the homelab environment.

Although the internal implementation may evolve over time, the overall workflow remains consistent to ensure predictable and repeatable results.

The general Recovery Point workflow consists of the following stages:

1. Initialize the Recovery Point.
2. Generate the Recovery Point identifier.
3. Create the directory structure.
4. Collect Docker configuration.
5. Archive project documentation.
6. Gather Proxmox host information.
7. Generate the Recovery Point Manifest.
8. Calculate file checksums.
9. Perform verification.
10. Generate execution logs.
11. Complete the Recovery Point.

Each stage contributes to producing a complete and verifiable Recovery Point.

---

# Recovery Point Workflow

The simplified workflow is illustrated below.

```
Initialize
     │
     ▼
Generate Recovery Point ID
     │
     ▼
Create Directory Structure
     │
     ▼
Collect System Information
     │
     ▼

     │
     ▼

     │
     ▼

     │

     │
     ▼

```

Each stage builds upon the previous stage. If an error occurs, CBART records the failure within the execution log while preserving as much diagnostic information as possible.

# Recovery Verification

A Recovery Point should never be assumed to be valid simply because it was created successfully.

CBART performs verification after the collection process to confirm that expected artifacts were generated and remain accessible.

Typical verification includes:

- Directory structure validation
- Manifest validation
- Documentation archive validation
- Docker backup validation
- Proxmox information validation
- Checksum generation validation
- Verification report generation

Verification provides confidence that the Recovery Point can be relied upon during future recovery operations.

---

A typical summary may resemble the following:

```

[PASS] Documentation Archive
[PASS] Recovery Manifest
[PASS] Docker Backups
[PASS] Proxmox Information
[PASS] Checksums Generated
[PASS] Verification Report

```

This summary provides an immediate indication that the Recovery Point completed successfully and that all required components were verified.

# Recovery Point Retention

Recovery Points represent historical snapshots of the environment and should be retained according to the operational requirements of the homelab.

Retention policies may vary depending on available storage, project milestones, and recovery objectives.

For example:

- Create Recovery Points before significant system changes.
- Create Recovery Points after major milestones.
- Preserve Recovery Points associated with production releases.
- Archive Recovery Points before performing upgrades or migrations.

A consistent retention strategy provides valuable historical context while ensuring important Recovery Points remain available when needed.

---

# Best Practices

Creating Recovery Points is only one part of an effective backup and recovery strategy. Long-term success depends upon creating Recovery Points consistently, verifying their integrity, and maintaining them as part of the normal operational workflow.

The following recommendations represent best practices for using CBART.

## Create Recovery Points Before Major Changes

Generate a Recovery Point before performing any significant changes to the homelab, including:

- Operating system upgrades
- Docker image updates
- Service deployments
- Network reconfiguration
- Storage modifications
- Infrastructure migrations

Capturing the current environment before changes provides a known-good reference should recovery become necessary.

---

## Verify Every Recovery Point

A Recovery Point should never be considered complete until verification has finished successfully.

Always review:

- Recovery Verification Summary
- Execution log
- Verification report
- Recovery Point Manifest

Any reported failures should be investigated before relying on the Recovery Point for disaster recovery.

---

## Archive Important Recovery Points

Not every Recovery Point needs to be retained indefinitely.

However, Recovery Points created during significant milestones should be archived.

Examples include:

- Initial homelab deployment
- Major application releases
- Infrastructure redesigns
- Hardware upgrades
- Production migrations
- Portfolio milestones

Archived Recovery Points provide valuable historical references while preserving important stages of the project's evolution.

---

## Test Recovery Procedures

Backups are only useful if they can be used successfully during recovery.

Periodically review Recovery Points to ensure:

- Documentation is complete.
- Required artifacts are present.
- Verification reports indicate success.
- Recovery procedures remain accurate.
- Recovery documentation reflects the current environment.

Routine validation helps identify problems before an actual recovery event occurs.

---

# Common Mistakes

The following issues commonly reduce the effectiveness of Recovery Points.

## Skipping Verification

Generating a Recovery Point without reviewing verification results may allow incomplete or invalid Recovery Points to go unnoticed.

---

## Inconsistent Scheduling

Creating Recovery Points only occasionally increases the likelihood of losing important configuration changes.

Develop a consistent schedule appropriate for the environment.

---

## Ignoring Documentation

Configuration files alone rarely provide sufficient information to rebuild an environment.

Documentation should evolve alongside the infrastructure and be included in every Recovery Point.

---

## Deleting Historical Recovery Points Too Early

Older Recovery Points often provide valuable insight into previous configurations, implementation decisions, or troubleshooting efforts.

Retain milestone Recovery Points whenever practical.

---

# Recovery Checklist

Before considering a Recovery Point complete, confirm the following:

- Recovery Point completed successfully.
- Recovery Verification Summary indicates success.
- Recovery Manifest was generated.
- Documentation archive exists.
- Docker configuration was collected.
- Proxmox information was captured.
- Checksums were generated.
- Verification report was created.
- Execution log contains no unexpected errors.
- Recovery Point has been archived if appropriate.

Completing this checklist helps ensure that Recovery Points remain reliable and usable when they are needed most.
